DESIGN:
RECOMMENDED ARCHITECTURE: ride the real interactive session. Spawning is the fallback, not the default.

The crux question was framed as "is riding the REAL interactive session strictly necessary, or is a spawned local session with the same config good enough?" The config-loading answer is that spawning is good enough — I measured a non-bare `claude -p` loading 162 tools, 191 skills, 254 commands, 16 plugins, 18 MCP servers and the project memory directory, exactly as the docs promise. But three other things break the tie decisively toward the real session.

1. BILLING BUCKET. Anthropic has already drafted, announced and paused a change that would carve `claude -p` and Agent SDK usage out of subscription limits and overflow it to "standard API rates". Interactive session usage was never in that carve-out. A seshi that spawns `-p` processes is one Anthropic changelog away from silently violating constraint (j). A seshi that injects messages into an already-running interactive session is not. This is the argument that should decide it.

2. LIVE MCP AUTH STATE AND CONNECTORS. A spawned session inherits the keychain's mcpOAuth blob, so locally-configured OAuth MCPs carry over. But claude.ai connectors do not exist in the CLI at all — `claude mcp list` cannot see the 19 connectors this account has used. If Dave's 2D-to-3D expertise is in a Drive folder reachable only through his desktop app's connector, only his real desktop session can fetch it.

3. CONVERSATION HISTORY AND WORKING STATE. The real session already holds the thread Jake is in the middle of. That is the "advocate who knows me" property from answer (b), and it is not reconstructible from config files.

CONCRETE SHAPE

Layer 1, the wire. A dumb relay carrying signed JSON envelopes between machines. No model, no Anthropic call, no interpretation. Any transport Jake likes. This layer is where the token-internality guarantee is enforced and it is enforced trivially, by the layer having no intelligence.

Layer 2, the local endpoint. A small non-Claude daemon per machine (Node or Python, no LLM) that owns: the session scratchpad, relationship memory, the trust-tier policy for each contact, and the inbound/outbound queue. It talks to the local Claude session over the existing peer bus, and it is the thing that survives when a session is closed — which is what makes answer (f)'s resumability work.

Layer 3, the agent. Jake's real interactive session, addressed via the local bus. Inbound counterpart messages arrive as messages into the live session. Because ~/.claude/sessions/<pid>.json already carries `status` (idle/busy), `waitingFor`, `tempo` and a `bridgeSessionId` field, the daemon can tell whether Jake's agent is free, whether it is blocked waiting on the counterpart, and can hold messages accordingly. The substrate already models this.

The offline case, and the ONLY sanctioned use of spawning: when Jake has no session open and a message arrives, the daemon must not silently start burning quota. It should notify (macOS notification, the pattern Jake already uses in his Stop hook) and wait. If Jake explicitly opts in to "let it keep going while I'm away", the daemon spawns `claude -p --resume <sessionId>` — never `--bare` — with a per-turn budget and a hard turn ceiling, and it labels that usage differently in the ledger because it lives in the at-risk billing bucket. Frame it to Jake as: unattended mode is a different product with a different risk profile, not a transparent extension of attended mode.

SAFEGUARD, given Jake explicitly does not want hard caps (h). No caps. Instead:
- The daemon keeps a local ledger of tokens and turns per seshi session, computed from the transcript. It can report real numbers ($0.094/turn measured, ~$2.50 per 40-minute working session) because it cannot report a percentage of an unpublished weekly denominator.
- Loop detection, not budget caps. Two conditions catch a runaway without ever refusing to work: (a) no new commitments — if N consecutive exchanges add nothing to the scratchpad's decisions/open-questions list, the agents are circling; (b) semantic repetition — if a side restates a position it has already stated. Either trips a "we're going in circles, here's where we are" report to both humans. This is the deadlock escalation Jake described in (g), reached by measurement instead of by a turn counter.
- One genuine hard stop, and only one: a wall-clock ceiling on unattended mode. Attended mode needs none, because Jake is watching.
- The agent narrates spend proactively at natural boundaries ("we've been at this 25 minutes, about 180 turns between us, three decisions locked, one open"), which is exactly Jake's (h): "your claude should just communicate what's going on."

SECURITY NOTE THAT AFFECTS THE TRUST TIERS. CLAUDE_CODE_MESSAGING_SOCKET and CLAUDE_CODE_MESSAGING_TOKEN are exported into the environment of every Bash tool call. Any shell command Jake's session runs can address the entire local peer bus directly, bypassing the SendMessage tool and its permissions. So tier 3 ("propose writes with human approval") cannot be enforced by tool permissions alone if the counterpart can get a shell command executed. Tier 3 needs the daemon to be the only thing that touches the bus on seshi's behalf, and needs counterpart-originated content to never reach a Bash invocation unreviewed.

TIER 4 RECOMMENDATION. Ship tiers 1-3. Document tier 4, default it off, and put the Consumer Terms §2 language in front of anyone who enables it. Not because the risk of enforcement is high, but because Jake is open-sourcing this and the project should not be the reason someone else's account gets actioned.

RISKS:
- THE BIG ONE: Anthropic's paused Agent SDK billing change. The support article says `claude -p`, the SDK and third-party subscription apps were to move to a separate monthly credit that overflows to "standard API rates", that the change is paused, that the credit "isn't available", and that they are "working to update the plan". If it ships, any seshi that spawns `-p` becomes API usage and directly violates constraint (j) with no code change on Jake's side. Mitigation: architect around the real interactive session; treat spawning as an explicitly-labelled, opt-in unattended mode.
- SECOND ORDER OF THE SAME RISK: the docs state "`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." Bare mode cannot read OAuth. A seshi that shells out to `claude -p` today could start demanding ANTHROPIC_API_KEY after an update. Pin behaviour by passing flags explicitly and assert on apiKeySource in the init event; fail loudly rather than falling back to an API key.
- Consumer Terms §2 "You also may not make your Account available to anyone else." Trust tier 4 (full agency both ways) is the configuration most exposed to that reading. Genuine ambiguity, not a settled question. Higher stakes because Jake is open-sourcing it and other people's accounts are at risk, not just his.
- Anthropic is actively writing agent policy — the agents article exists but says nothing about agent-to-agent systems, relay between accounts, or disclosure. Absence of a rule today is not a rule in your favour tomorrow. Keep the relay layer swappable and be ready for policy language to arrive.
- Runaway loop economics: at the measured $0.094/turn on Opus, two unattended agents can consume a very large amount of both people's quota in an hour, and Jake explicitly does not want hard caps. Loop detection is the answer, but it is a heuristic and it will sometimes fail. Unattended mode needs at minimum a wall-clock ceiling even though Jake dislikes caps — frame it as a safety interlock, not a budget.
- Environment leakage of the bus credentials into every Bash call means tool-level permissions are not a sufficient boundary for trust tier 3. The daemon must mediate, and counterpart-authored text must never flow into a shell invocation unreviewed. Treat counterpart messages as untrusted input throughout — prompt injection from a friend's compromised agent is a real threat model here.
- The desktop/CLI connector asymmetry will produce confusing behaviour: the same person's agent will be measurably smarter in the desktop app than in the terminal, and seshi has no way to signal that. Surface which surface a peer is on so the other side knows what its counterpart could and could not reach.
- Peer-bus internals are undocumented and version-coupled. The registry schema I read (peerProtocol 1, kind enum, bridgeSessionId, tempo, needs) is minified bundle internals from 2.1.239. Anthropic can change it in any release. Build against ListAgents/SendMessage as the stable surface and treat direct socket access as an escape hatch, not the foundation.
- Session records are ephemeral and pid-keyed — they vanish when the process exits. Jake's requirement (f) that sessions be resumable cannot be satisfied by the bus alone; the daemon must own durable state or context genuinely will be lost, which is the exact failure Jake called out as "annoying".
- total_cost_usd is documented as a client-side estimate that "can differ from your actual bill", and on a subscription there is no bill to differ from. Any spend figure seshi shows is an equivalence measure. Label it that way or it will erode trust the first time it disagrees with something Anthropic shows.

This determines whether seshi feels conversational or turn-locked, and it is Stream A/B's to answer.
- Does `claude -p --resume <id>` against a session that is CURRENTLY OPEN interactively conflict, fork, or corrupt the transcript? Critical for the unattended fallback, and I did not test it because the failure mode could damage a live session.
- What is the actual weekly quota denominator on Max 20x? Anthropic no longer publishes it and the local caches do not hold it. If there is an authenticated endpoint the CLI reads for the /usage view, seshi could surface real remaining capacity instead of raw token counts — worth one look at the network calls the CLI makes on startup.
- Will Anthropic's paused Agent SDK billing change ship, and in what form? This single question determines whether spawning is a legitimate fallback or a trap. Worth Jake asking support directly, framed as "I'm building an open-source tool where two subscribers' Claude Code sessions exchange messages, each thinking on its own subscription — is that within terms, and should I avoid `claude -p`?" A written answer is worth more than any amount of clause-reading, including mine.
- Where exactly does Anthropic draw the line on trust tier 4? The §2 language is the only clause that bites, and the honest answer is that nobody knows how it applies to a friend's agent proposing a write that the owner's agent executes. Worth asking in the same support conversation.
- Does the desktop app pass settingSources to the CLI it spawns, or rely on the CLI default? I found settingSources referenced at eleven offsets in app.asar but did not decode the call site. If it passes an explicit narrow list, desktop Claude Code sessions may load less local knowledge than terminal ones, which would invert the connector advantage.
